## Controlled rollback procedure, only after separate production approval

1. Confirm Winserve site root, Production environment, production database identity, protected backup, and active 125-file manifest. Rehash all current managed files and stop on drift.
2. Preserve a complete copy of the current application package and current manifest for forward recovery. Preserve existing `web.config`, appsettings, IIS variables, secrets, the sibling `data` directory, and the SQL database unchanged.
3. Enter maintenance mode and stop ordering writes for the short file-swap window. Do not start the POS until the candidate files have been fully verified.
4. Place a rollback-pending manifest carrying the exact 122 previous hashes and explicit state `installed, health pending`; upload only the 64 differing files from the verified local copy. Verify each uploaded file's remote SHA-256. Leave the four unchanged dependency DLLs untouched after confirming their live hashes.
5. Remove the three new `end-of-day-print.js` variants only after confirming their names and that they were introduced by the failed release. Verify the resulting managed file set against the previous manifest. Do not delete server configuration, data, logs, or unrelated files.
6. Start the previous application. Retry `/health` for a bounded period and fail closed if it does not return 200. Check staff login, menu loading, order queue, and essential POS navigation using non-destructive checks; confirm website-to-POS menu integration. Avoid real payment or order creation during the gate.
7. Only after the application and functional checks pass, atomically promote the previous manifest as active and record `healthy`. Remove maintenance mode last, then repeat external health and menu checks. If a check fails, retain maintenance and the pending/failed state; preserve diagnostics and do not claim success.

No SQL migration, restore or downgrade is part of this plan.
