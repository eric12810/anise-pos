# POS production release procedure

The staging dry-run publishes the exact reviewed package as a retained artifact. Production accepts only a selected artifact/run and never rebuilds it. `production-preflight.py` inspects `Program.cs` startup SQL and numbered scripts offline; it does not start the API or connect to SQL.

Run the production workflow with the exact successful staging dry-run ID. The workflow resolves the matching artifact and commit through the GitHub API, then requires the protected `production` environment reviewer, separate FTPS credentials, exact approved host/root and database variables, and the protected `PROD_BACKUP_CONFIRMED=true` production variable. Database identity must have been verified by an authorised read-only session before enabling a release; this workflow does not perform that check. Existing `web.config`, appsettings, data and logs remain server-side, and no remote deletion is allowed.

Production requires an existing verified `.anise-pos-production-deployment.json` baseline in the approved remote root. An empty root or missing manifest is not treated as a first-deployment approval; establish and independently verify the production baseline before enabling uploads. Retain the previous artifact and deployment manifest. Roll back by selecting the previous approved artifact through the same guarded workflow after health-check failure review. Never use API startup to discover a production connection because startup SQL can alter schema.

The workflow reads `LIVE_FTPS_HOST`, `LIVE_FTPS_USERNAME`, and `LIVE_FTPS_PASSWORD` from repository secrets and `PROD_FTPS_ROOT` from a repository or production-environment variable. The host may be shared with staging only when the production account, approved root, and verified production baseline identity are distinct. The root must never be inferred from the application hostname.
